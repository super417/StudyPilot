# StudyPilot 项目体检 · 缺口清单（2026-10-04）

> 对照 `.kiro/specs/study-pilot/` 与实测代码。**Kiro spec 98 项任务全打勾**，功能能跑通；
> 但「不完整」感来自 spec 覆盖不到的三类真实缺口：**功能闭环 / 数据完整性 / 演示风险**。

---

## A. 功能闭环缺口（用户点得到、感知最直接）

| # | 缺口 | 现状 | 详见 |
|---|---|---|---|
| A1 | 规划只有阶段，看不到「每天干什么」 | `planner_service._PLAN_SYSTEM_PROMPT` 只要求「daily_tasks 每阶段至少 1 条」；前端 `PhaseList` 不可展开，`GET /api/daily-tasks` 只支持按单日查 | `需求补充-Roadmap每日任务与错题本.md` G1 + G2 |
| A2 | 学完不能自测（没有练习题） | 无出题能力，无 `practice_questions` 表 | 同上 G5 |
| A3 | 错题本没有「习题 / 错题」分区 | `MistakeBookPage` 是单列表 + 顶部筛选 | 同上 G4 |
| A4 | **没有历史规划入口** | `routers/plans.py` 只有 `GET /latest`，无列表接口 | 见下 |

**A4 说明**：用户重新规划后，旧规划只能从数据库翻。演示时说「你的路线会跟着你变化」，
却拿不出「变化前 vs 变化后」的对照 —— 这条能力是断的。
修法：新增 `GET /api/plans`（返回 id / goalName / updatedAt / 阶段数），前端加规划切换器。

## B. 数据完整性隐患（最容易被忽略，危害最大）

### B1 · 重新规划会抹掉全部历史每日任务与阶段进度 ⚠️

`planner_service._write_plan_structure`（约 578 行）的既有设计是**先删后建**：

```python
session.execute(delete(DailyTask).where(DailyTask.plan_id == plan.id))
session.execute(delete(Phase).where(Phase.plan_id == plan.id))
```

`POST /api/plans/{plan_id}/regenerate` 复用它（plan 行 UPDATE，子表整体重建）。后果：

- 学了一个月 → 点一次「重新规划」→ **30 天的 DailyTask 记录、阶段进度全部归零**。
- `metrics_service.compute_overview` 的 `phaseProgress`、今日任务判定都依赖 `DailyTask`，会同步失真。
- `CheckIn`（打卡）有独立 `user_id`，**不受影响** —— 所以表现是「打卡记录还在，但任务进度没了」，用户会困惑。

需求 10 只写了「规划可中途修改」，**没规定要保护历史** —— 这是 spec 的盲区，不是实现 bug。

**修法（二选一）**：
1. `regenerate` 时保留 `task_date < today` 的历史任务，只重建今天及以后；
2. 给 `Phase` / `DailyTask` 加 `archived_at`，重新规划时归档而非删除。

方案 1 改动小，推荐。

### B2 · `CheckIn` 没有「一天一条」约束

同日多次打卡会累加 `total_minutes`。需求 15.2 支持多条、4.7 文案偏单数 —— **需求歧义，未擅自加约束**。

## C. 演示风险（竞赛现场会当场露馅）

### C1 · `#/mainframe` 演示首屏需要登录

`App.tsx` 的鉴权判断排在 `showMainframe` 之前 → 评委直接打开该地址会先落到 AuthPage。
hash 不清，登录后能自动回跳，但**评委看不到「打开即演示」的效果**。

修法：给演示页开免登录白名单，或加 `?demo=1` 开关。

### C2 · 助手的三个加分点后端无实现

long_text 里要求、但 Kiro spec 里**没有**的三项：

| 能力 | 现状 |
|---|---|
| RAG 引用溯源 | 无。`assistant_service.build_chat_messages` 只在 prompt 里写「知识库摘录：无（请勿伪造引用）」 |
| Function Calling 工具调用展示 | 无 |
| 防幻觉拦截 | 只有 `assistant_service.is_off_topic` 一个离题过滤 |

这三项要新增后端能力，与「禁止修改后端」红线冲突，**需先拍板**。

## D. 工程健壮性

| # | 问题 | 影响 |
|---|---|---|
| D1 | **前端没有 ErrorBoundary** | 任一组件抛错 → 整页白屏，没有兜底 UI |
| D2 | **没有 CI** | 无 `.github/workflows`；测试靠手跑，改动容易静默破坏 |
| D3 | **过时注释误导** | `frontend/src/mocks/profileMock.ts` 里 6 条 `TODO(backend): 对接 GET /api/xxx（待后端实现）`，实际**早已对接**（`profileStudyApi.ts` 全部走真实接口）。留着会让 Cursor 重复劳动 |
| D4 | `ai_proxy.py:303` TODO | 不同 provider 的 stream delta 格式差异未处理（如 OpenAI 的 `delta.reasoning_content`） |
| D5 | 166 条 pydantic 警告 | `CheckInPayload` 的 `alias_generator=_to_camel` 对 `energy` / `note` 这类单词字段生成了同名 alias，pydantic 报 `UnsupportedFieldAttributeWarning`。**无害但是噪音**，会淹没真问题 |

## E. 测试现状（实测 2026-10-04）

```
298 passed, 55 subtests passed, 166 warnings in 279.48s
```

- 后端 **全绿**。298 个测试 + 55 个 subtest，跑完约 4 分 40 秒（Hypothesis 150 次迭代占大头）。
- 覆盖面广：33 个测试文件，含 4 个属性测试（planner / study / security / mistake-document）。
- 前端 8 个 vitest 文件，含 1 个视觉快照测试。
- **测试不是短板，是项目最扎实的部分。** 上面 A/B/C 那些缺口，spec 和测试都没覆盖到 ——
  因为它们不是「实现错了」，是「压根没规划进去」。

## F. 建议优先级

### P0 · 演示前必须处理

1. **A1 规划粒度** —— 「生成规划」是演示主路径，点开 Roadmap 空荡荡最尴尬
2. **C1 演示页登录** —— 评委第一眼
3. **A4 历史规划列表** —— 否则「路线会跟着你变化」演不出来

### P1 · 演示前尽量做

4. **B1 数据完整性** —— 演示前反复重新规划会把数据搞乱
5. **A3 错题本分区**（纯前端，成本低）
6. **D3 清掉过时注释**（5 分钟）

### P2 · 有余力再做

7. **A2 练习出题**（最大一块，要新表 + LLM）
8. **C2 助手引用溯源**（加分项，需后端授权）
9. **D1 ErrorBoundary**
10. **D2 CI**

## 一句话总结

项目不是「没做完」，是**做完的部分很扎实，没做的是几个闭环**：
规划没细到天、学完不能测、错题本不合心智、重新规划会清空历史、演示页要登录。

其中 **B1（重新规划清空历史）** 和 **C1（演示页要登录）** 是这轮体检新发现的，
上一份需求文档里没有，优先处理。

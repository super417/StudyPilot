## 1. 一句话定位

**面向在修 AI 微专业 / AI 通识课的非计算机专业学生，做就业方向的技能差距诊断与掌握度验证。**

不做通用学习助手，不做考研工具，不做教育游戏。

## 2. 目标用户

| 维度 | 取值 |
|---|---|
| 专业 | 非计算机专业（财会、经管、师范、教育等） |
| 年级 | 大二至大四 |
| 场景 | 正在修或即将修 AI 微专业 / AI 通识课 |
| 动机 | 提升就业竞争力，要把课程变成简历上能证明的能力 |

**为什么是这个群体**：AI 正在成为高校公共基础课，班级大、学生基础差异大（同一班里有会写代码的也有没碰过的），教师无法逐个跟踪；而他们的目标明确——不是"学得开心"，是"能证明我会什么"。

## 3. 核心主张

> **用 AI 检测和阻断"认知投降"，而不是用 AI 替学生完成学习。**

"认知投降"（cognitive surrender）指学生遇到卡点立刻把思考外包给 AI，得到答案却失去获得答案的能力。它的典型表现是**作品与能力脱钩**：能交一篇漂亮论文却没读过文献，能交跑得通的代码却讲不出逻辑。

产品对策是同一个界面上的两个数：

- **完成度**：任务层面的进度（打卡是弱证据）
- **掌握度**：能力层面的证据（测验、讲解、综合题）

两者长期背离时，系统把它变成可修复的闭环，而不是弹一个警告。

| 赛题方向 | 落点 |

| **2 号 场景化轻量 RAG 知识库（主打）** | 课程库与资料索引、相关检索、回答出处；出题与判分必须引用检索到的原文片段，检索不到就不出题 |

多接口组合调用体现为：检索 → 出题 → 判分 → 讲解评估 → 路线生成，每个模块独立可替换。

### 5.1 检索方案：BM25，不用向量（2026-10-14 定）

- 检索做成单一接口 `rank(query, chunks, k) -> [(chunk, score)]`，当前实现为 BM25，可替换。
- 中文按**字符二元组**建倒排，不引 jieba；英文按空格切词。
- **不引向量库、不引本地 embedding 模型、不做"有 embeddings 就走向量"的兼容分支。**

理由（答辩口径）：产品是用户自填 Key（默认 DeepSeek），多数供应商没有 embeddings 端点，向量链路在默认配置下就断；BM25 零新依赖、离线可跑、结果确定、可写单元测试；个人学习资料量级几百个片段，内存计算足够。代价是同义改述的召回弱于向量，如实承认。

## 6. 差异化（相对同类项目）

1. **"讲给 AI 听"的原文锚定评分** —— 用户口述概念，AI 扮演小白追问两轮，评分不是印象分，而是对齐回检索原文，输出"讲对了什么（引自第 X 节）/ 漏了什么 / 错在哪"。
2. **完成度与掌握度的系统性背离检测** —— 计算差值，自动聚类低掌握知识点，生成补强任务，补强后重测并展示变化。
3. **约束求解式的路线调整** —— 延期时给三个选项并预测各自代价（学完时间、掌握深度、风险），用户拍板后才生效；选哪个由错因分布决定，不由模型自由发挥。

## 7. 商业模式

- **B 端（主）**：高校 AI 微专业 / 通识课按班级采购；教师端看班级掌握度热力图，直接指导下一节课讲什么。**比赛版不实现教师端**，只在方案里讲。
- **C 端（辅）**：个人免费使用完整闭环，高级版解锁能力报告导出、简历技能映射。
- **就业服务对接**：能力报告可对接学校就业指导中心。

- **撤销补强 = 连同已完成记录一并回滚**（2026-10-16 用户裁定，**有意为之**，非遗漏）。不做撤销前拦截、不加弹窗警示；补一条测试钉住该行为，防止后人当 bug「顺手修好」。

## 10. 三项核心缺口与架构决定

### 10.1 已修（第 4–5 批，2026-10-14 至 10-15）

| # | 原问题 | 修法 |
|---|---|---|
| 1 | 检索不存在：所有片段按 `chunk_index` 拼接后截断 20000 字，没有 query 参数 | BM25 检索（见 5.1）；检索为空则不出题 |
| 2 | 判分不存在：对错由用户自己点 | 系统判分；判分失败不写证据、不默认答对；无原文时理由中不得出现"资料中 / 原文"类引用 |
| 3 | 掌握度与完成度是同一个数：按课程名子串匹配任务算完成率 | 新建 append-only 证据表，掌握度由证据现算；名称匹配已删除 |

### 10.2 架构决定（后续批次须遵守）

- **证据表 `mastery_evidence` 只追加不覆写**，保留每次作答，支撑"补强后重测并展示变化"。字段含 `knowledge_point`、`question_id`、`evidence_type`（quiz / explanation / composite，后两种待实现）、`result`（correct / partial / wrong）、`error_tag`、`grade_reason` 等。
- **能力节点 = 阶段（Phase）**。`knowledge_point` 存 `phase_id`，由 题目 → 来源任务 → 阶段 推出；推不出则为 null，入库但不计入任何节点。原定"粒度到章-节"作废：阶段与课程两条数据链之间没有关联，章节号填不上。
- **派生指标不入库，事件记录照存。** 掌握度能由证据随时算出，每次读取现算，不存列、不缓存；AI 生成的复盘文字事后无法重算，照存。掌握度无证据时为 null，界面显示"暂无掌握度证据"，**不得显示为 0%**。
- **判据补充（2026-10-15）**：一个存库字段是否该删，看它**算错了会怎样**，不看它是否可算。
  - 算错了会让用户看到一个**错的数** → 派生数值，删列现算（`progress_percent`、`mastery_avg`）。
  - 算错了只会让**选中项或排序**不对 → 查询键 / 状态标记，属另一类。保留的前提是：**写入方唯一，且在每次相关变更后都重算**。满足则保留并补一条不变量测试；不满足则先修漂移，再谈存删。
  - **不得因为「它可算」就删查询键**——删查询键要重写查询，改动面与收益不成比例，还会撞上验收闸门。
- **双环同键、同窗口**：完成度与掌握度按同一个 `phase_id`、同一个时间窗口现算；完成度由每日任务完成情况算出，不读 `Phase.progress_percent`。
- **背离阈值 30 个百分点**，为具名常量，属**经验值、非研究结论**，材料中不得包装成科学阈值。**掌握度旁必须显示证据条数**（如"基于 3 次作答"）——1 次作答即可触发背离提示，样本量必须摆在台面上。

### 10.8 第 11 批复审后的两处发现与裁定（2026-10-16）

第 11 批提交后独立复核（迁移升降实跑、受影响 14 条测试实跑）通过，同时发现两处，裁定如下。

**发现 1：迁移与 ORM 模型索引漂移。**

迁移 `a6b7c8d9e0f1`（alembic revision ID）用 `op.create_index` 建了 `ix_reinforce_task_evidence_evidence_id`，但模型 `ReinforceTaskEvidence` 未声明 `index=True`。后果：**alembic 建的库有该索引，`Base.metadata.create_all` 建的库（测试走这条）没有**——两套 schema 不一致，测试永远看不到这个索引。

**裁定：补模型 `index=True`**（并入第 11 批补 2）。理由：
- 项目**已有先例**是「迁移与模型声明双写」：迁移 `c4f1a7b93e20`（**alembic revision ID，不是 git 提交号**）为 `conversations.user_id` 与 `chat_messages.conversation_id` 建了索引，对应模型也各声明了 `index=True`。本次是漏标，非有意为之。

**发现 2：`_apply_reinforce` 对已在关联表中的证据静默跳过。**

`reinforce_service.py` 中为 `if evidence_id in already: continue`，仅当**全部**被跳过时才抛 `AdjustmentConflictError`。即预览与确认之间被抢先写入时，会写入一个子集。

**裁定：接受现状，补注释说明意图，不改逻辑**（并入第 11 批补 2）。理由：
- 此处语义是**幂等**——「这条证据已有任务，跳过它，继续写其他」。竞态下子集写入比「一条冲突就全部不写」对用户更有用。
- 全部跳过才报错已兜住最坏情况（不会写入空补强）。
- 真实风险是后人**不知道这是有意为之**，顺手改成「有一条跳过即冲突」——破坏语义却显得更整齐。故**加注释写清意图**，而非改行为。

> **与 `confirm_reinforce` 的关系**：该函数用 `UPDATE ... WHERE status='pending'` 做乐观锁（`:95-105`），锁后重查 `basis_fingerprint`（`:116`），并在 `expire_all` 后重算 `_covered_evidence_ids`，故「已被别的确认写入」的证据会被正确排除。发现 2 描述的是**残留窗口**，非主路径缺陷。

**裁定：三样合并为一页**，不拆三个页面。理由：演示时一屏讲完，且星图、航线、阶段测验共享同一份「每日表现 + 阶段进度」数据。

**星星口径（2026-10-19 用户定，A 方案）**：

| 当日作答正确率 | 星 |
|---|---|
| ≥ 60%（含） | 金星（笑脸） |
| 40% – 60%（不含 60%） | 蓝星（笑脸） |
| < 40% | 灰星（笑脸） |
| **当日未作答** | **深灰哭脸星** |

- 正确率按当日 `MasteryEvidence` 计算，沿用 `_EVIDENCE_SCORE`：`correct=100 / partial=50 / wrong=0`，按条平均。**`partial` 记 50%，落在蓝档**，这是保留三色的理由——partial 与 wrong 是不同的事实，合并成一个灰星等于抹掉「部分对」。
- **哭脸星不计入任何正确率统计**。它只表示「这天没作答」，**不是「这天 0%」**。同理，没作答的日子**不得画成灰星**——灰星是「答了但很差」，两者必须区分。

**正反馈三层（微 / 小 / 大）**：鼓励语**只绑定可验证的历史数据**，例如「这三天正确率从 40% 升到 67%」「连续 5 天完成全部任务」。

**明确禁止「学习效率提升」这类表述**：`DailyTask` **没有完成时间戳**（只有 `task_date` 与 `status`），`CheckIn.duration_minutes` 是用户自报打卡时长，不是真实用时。测不出来的东西不许说。

**自动顺延（改为「自动生成预览 + 提醒」）**：检测到当日任务未完成时，**自动生成一份顺延预览并提醒**，用户确认后生效。**不得自动改写计划**。

理由：项目从第 10 批起确立「任何计划改动都要预览 → 用户确认 → 生效，且可撤销」。自动改写会让撤销失去意义——系统在用户不知情时改了计划，用户事后点撤销，撤的是哪一次？改成预览也几乎不用新写代码：`remedy_service` 已有 `carried_from_id` 顺延机制与容量计算，接一个触发即可。

**提醒文案**：「你有 3 项任务未完成，{助手名}建议顺延到明天，确认后即可生效 ☺」（助手名见 10.14）。

**明确不做**：时间/截止日期滑块（用户 2026-10-19 砍掉）。

## 12. 流程纪律

> **纪律：复审与提交的先后，按批次风险分两类。**
>
> **一、高风险批：先复审、后提交。** 属下列任一即高风险——**需要迁移**的改动（建表 / 删列 / 改列 / 加索引迁移）、**闸门放行过的测试**、**真实模型调用**、或改动跨前后端契约。此类须先出具批次报告并完成复审（分级见 12.1），方可本地 commit，**不得以「先提交、事后补复审」代替**。
>
> **判据按「是否需要迁移、是否难回退」定，不按「文件里有没有出现模型」定**：只改 ORM 声明而不生成迁移（如补 `index=True` 让 `create_all` 一侧与已建库对齐）、不动已有 schema、不改查询语义的，属低风险，走第二类。
>
> **二、低风险批：提交不设前置复审，抽查在下一批开工前完成。** 除第一类以外的批次都属此类——包括只增删测试的、只改 ORM 声明而不生成迁移的、只加注释或改文案的。
>
> **抽查动作放在提交前还是提交后，本条不规定。** 命令本来就要跑，顺手在提交前看一眼 diff、跑一次定向测试，与落盘后再跑**没有信息差**。真正的要求是**谁审**：抽查必须由代码实现对话**独立核过**（自己跑命令、自己看 diff），不得只采信 Cursor 自报；commit message 仍须标明复核方式（如「提交后抽查」）。
>
> **三、跨两类不变的一条**：**未复审的提交只算「已落盘」，不算「已验收」，不得据它做判断**——不据此排后续批次、不据此更新台账、不据此写对外材料。第 11 批的教训正是这一条：总规划把一次未复审的提交当成事实，就「钉住撤销回滚的测试是否存在」下了落空的指令，台账一度记着一条并不存在于仓库的测试。
>
> **不适用**：文档类改动（如本文件），由代码实现对话直接提交，不受前两类限制。
>
> **事后发现问题的处理**：不 amend、不 rebase（见 12.3），**以新增 commit 修正**。

### 12.1 复审分级（2026-10-16 起）

**测试输出、`git status`、提交记录本身即执行结果**，日常批次不完整重跑全量。

仅以下**三种情况**须独立重跑：

1. 迁移或删列等**难回退**改动；
2. **闸门放行过**的测试（如 10.5 那 9 行）；
3. 报告中的**数字与命令输出对不上**。

**记录已验收时须标注复核方式与时间点**：写「提交前已复审」还是「提交后独立复核」，两者含义不同，不得混写。第 11 批属后者——两个提交落盘后才做独立复核（迁移升降实跑、受影响 14 条测试实跑）。

### 12.2 批次报告末尾两行

自第 11 批起，批次报告末尾固定两行：

```
需总规划确认：是/否
需代码实现-cursor确认：是/否
```

两行**互不从属**：各自是真实判断，不得机械套用。

### 12.3 Git 与推送分工

- **本地 commit** 归**代码实现-cursor 对话**；Cursor 不执行任何 Git 操作。
- **推送**归 workbuddy 定时任务（每晚 21:00 自动），不由谁手动推。
- **历史不可改写**：不得 rebase、不得改写既有 commit message（`.git` 历史中 4 处「智航」保留原样）。
